# Demonstration: a hypothetical printable-paper tool

**Nature of this example:** A **hypothetical study**, not a validation claim. No paid customers, user interviews, demand measurements or real prototypes have been established in this example. The purpose is to demonstrate honest use of stages and evidence gates.

## 0. Problem observation

Possible customer: independent designer, zine maker or creative hobbyist. Possible job: produce a useful, customisable object using ordinary A4 paper and a home printer. Possible friction: scattered templates, unfamiliar assembly procedures and print configuration. **Evidence status:** assumption, pending customer observation. Current alternatives to research: free templates, general graphics software, publisher tools and manual cutting/folding instructions.

## 1. The 'secret' to test

"Some users may prefer a single task-specific maker that reliably produces an assembled object over a flexible design editor." This could change the product from general design software to a collection of exact printable templates and limited controls. **Disconfirmation:** Users consistently prefer generic templates or existing editors; target group has no substantial repeated need; completed physical output isn't reliable.

## 2. Reverse-engineered outcome

Successfully print, assemble and use one selected paper object. Necessary components: accurate geometry, print layout, clear material requirements, user-input validation, physical folding/cutting guidance, and repeatable PDF export.

Three candidate mechanisms:

1. Downloadable annotated PDF with no customisation.
2. Browser-based A4 maker with limited content entry and exact geometry.
3. Manual service producing a personalised file in response to customer data.

**Decision remains open** until user need, technical complexity and demand evidence are considered.

## 3. Seven Questions check (preliminary)

| Question | Status | Next test |
|---|---|---|
| Engineering | Unknown: printable output must work reliably | Build physical specimen and verify dimensions, folds and margins |
| Timing | Unknown: browser tools and home printing exist; reason for now unproven | Review current alternatives and customer workflow |
| Monopoly | Unknown: clear narrow customer group unvalidated | Research substitutes and first reachable community |
| People | Possible: single operator plus coding agent; physical QA still needed | Test deployment and actual print equipment |
| Distribution | Unproven | Identify 10 potential testers and permission-based outreach plan |
| Durability | Unproven | Check whether catalog quality, repeat uses and trust compound |
| Secret | Hypothesis only | Observe users choosing between generic template and guided maker |

## 4. First two proposed experiments

**A — feasibility:** Generate one exact A4 foldable object, test across declared printer settings and assemble physically. Pass if predeclared dimensional tolerances and assembly success are met. Fail if geometry/layout require excessive manual corrections. Document actual device, material and results.

**B — user evidence:** Observe real prospective users attempting the task with existing alternatives and then with a minimum template/maker; record completion, confusion, time and preferences. Predefine before the test what would justify interactive engineering. Do not generate participant quotations using an LLM.

## 5. Stage decision

**Stage:** Discovery / design. **Gate:** Not passed for full implementation. **Next step:** Obtain representative customer and physical feasibility evidence. GTM, price and audience are still hypotheses.


## 6. Intention and context preservation — worked demonstration, not verified user research

**Hypothetical operator intention:** make physical, practical A4 objects through a restrained browser interface. The intended result includes (a) usable print geometry, (b) genuinely understandable assembly, (c) a minimalist editorial interface rather than an elaborate SaaS dashboard, and (d) a complete first object rather than a large collection of incomplete templates.

**Technical agent receives:** approved intention, first-object scope, required A4 geometry, source printing constraints, explicit negative design constraints, acceptance fixture, sandbox-only permissions and physical-test escalation. It must not swap the product for a generic image editor or present a screen preview as physical verification.

**Potential drift:** an engineering agent creates a technically functional layout editor with a busy multi-panel UI; all automated layout tests pass. **021 decision:** functional status may be *pass* while intention fidelity is *fail*. The release is not approved until the experience aligns with the current intention or the operator formally changes it.

**Another potential drift:** a growth agent advertises print-perfect results on every home printer. This exceeds verified evidence. **021 decision:** the agent may propose a restrained, supportable claim, but may not publish the broader promise without actual tests and approval.
